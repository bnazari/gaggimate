This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

GaggiMate is an ESP32-based smart controller for espresso machines. This is **bnazari's fork** (`origin`) of `jniebuhr/gaggimate` (`upstream`), adapted for a **Rancilio Silvia**. The sim, native tests, nanopb comms, and embedded WebUI are **upstream** features (their `[GM-xxx]` comment tags reference upstream's Linear workspace); the fork's own delta is catalogued in "Fork changes vs upstream" below. Fork-added code marks itself with "(this fork)" in comments — keep doing that so divergences stay greppable.

Two separate ESP32 firmwares talk to each other over BLE:
- **Display** (`src/display/`) — LVGL touchscreen UI, WiFi, web server, plugins. The brains: profiles, brew orchestration, PID setpoint decisions. Built with `-e display` (LilyGo-T-RGB env), but the actual hardware (verified 2026-07-24) is a **466×466 round AMOLED with CST9217 touch** — the firmware's driver autodetect picks `AmoledDisplayDriver` at runtime, no config change needed.
- **Controller** (`src/controller/` + `lib/GaggiMateController/`) — the machine-side board driving heater/pump/valve peripherals with safety mechanisms (thermal runaway shutoff).

The BLE protocol is nanopb protobuf: schema at `lib/NanoPbComm/proto/gaggimate.proto`, with `gaggimate.pb.{c,h}` generated **at build time** (never committed) via `custom_nanopb_protos` in platformio.ini.

## Commands

```shell
# Firmware builds
pio run -e display                       # display firmware (LilyGo-T-RGB)
pio run -e controller                    # controller firmware
pio run -e display -t upload -t monitor  # flash + serial monitor (also: -e controller)

# Desktop simulator — real display firmware natively, SDL window, mocked BLE controller
pio run -e display-sim -t run            # build + launch (needs `brew install sdl2`)
./.pio/build/display-sim/program --screenshot shot.bmp 4000   # headless screenshot after 4000ms
# sim state (settings/profiles/history) persists in sim_data/ — delete to reset

# Tests (host-native, no hardware)
pio test -e native_autotune              # SIMC autotune unit tests (Unity)

# Web UI (Preact + Vite + Tailwind/daisyUI, needs Node 22 — `nvm use`)
cd web && npm run dev                    # dev server on :5173
cd web && npm run lint                   # eslint (lint:check for no-fix)
cd web && npm run format                 # prettier
scripts/build_webui.sh                   # build + embed into src/display/webassets/ (git-ignored)

# C++ formatting (clang-format via .clang-format; excludes src/display/ui/ and drivers/)
scripts/format.sh

# ESP32 crash analysis
python3 scripts/analyze_coredump.py <coredump.bin> [display|controller|...]
```

Other PlatformIO envs: `display-headless` (no screen/LVGL), `display-headless-8m` (Seeed XIAO ESP32-S3), and `display-sim`/`native_autotune` (both `platform = native`).

## Verifying display/UI changes

Prefer the simulator over hardware: it builds the unchanged firmware from `src/display/` (a few `#ifndef GAGGIMATE_SIM` guards aside) with host shims from `sim/` — `sim/platform/` (Arduino/FreeRTOS/FS/Preferences/WiFi shims), `sim/comms/` (mock BLE client + thermal/hydraulic MockController), `sim/driver/` (SDL2 ↔ LVGL), `sim/web/` (async web server shim). Everything runs as one cooperative loop on the main thread — `xTaskCreate` is a no-op. WebUI is served at http://localhost:8080/ while the sim runs. Compiled out in sim: MQTT, HomeKit, mDNS, WiFi watchdogs, BLE scales, OTA. Screenshot mode is the fast path for visual verification.

## Display firmware architecture (`src/display/`)

- `core/Controller.{h,cpp}` — central orchestrator: owns WiFi, BLE link to the machine controller, `ProfileManager`, `Settings`, mode/process state.
- `core/PluginManager` + `core/Event.h` — event-driven plugin system. All optional features are plugins in `plugins/` (WebUIPlugin, ShotHistoryPlugin, LedControlPlugin, BLEScalePlugin, MQTTPlugin, HomekitPlugin, watchdogs, ...). New functionality hooks in as a plugin listening to events, not by editing Controller.
- `core/process/` — active-task state machines: `BrewProcess`, `SteamProcess`, `GrindProcess`, `PumpProcess` behind a common `Process.h` interface.
- `core/Settings` — user preferences persisted via NVS Preferences.
- `ui/default/DefaultUI` + `ui/default/eez/` — LVGL screen code generated by **EEZ Studio** (project in `eez-ui/`); `drivers/` — per-board display drivers. Both are excluded from clang-format; don't hand-edit generated `eez/` files casually.
- `plugins/WebUIPlugin` serves the embedded WebUI and a WebSocket API (spec: `docs/websocket-api.yaml`).

## Web UI embedding (GM-106)

The Preact bundle is **not** on the LittleFS image. `scripts/build_webui.sh` builds `web/`, gzips assets, and `scripts/embed_webui.py` packs it into memory-mapped flash artifacts in `src/display/webassets/` (git-ignored; `scripts/embed_webui_pre.py` stubs an empty bundle at compile time if you haven't run it). LittleFS holds only profiles (`/p`) and shot history (`/h`), so OTA never touches user data. After changing anything in `web/`, rerun `scripts/build_webui.sh` before building display firmware or the sim.

## Hardware: GaggiMate Pro Rev 1.1 controller board

The machine runs a **GaggiMate Pro Rev 1.1** board (`GM_PRO_REV_11` in `lib/GaggiMateController/src/ControllerConfig.h`, autodetect value 4). Board connectors ↔ config pins:

| Connector | Signal | GPIO / config field |
|-----------|--------|---------------------|
| SSR outputs | heater SSR | 14 (`heaterPin`); SSR2 = 47 (`altPin`, steam SSR) |
| Screen header | display power + I2C | SCL 17 / SDA 18 / SDA2 39 (`scale*Pin`) |
| Buttons header | brew / steam switches | brew 38, steam 48 (+GND; inputs are active-low switches) |
| UART header | RX 44 / TX 43 | `sunriseSclPin`/`sunriseSdaPin` |
| J3 (pressure) | GND / X / Analog In / +5V | I2C transducer on 41/42 (`pressureScl/Sda`) |
| Temp terminals | T+/T− thermocouple | MAX31855 on SPI 6/7/4 (`maxSck/Cs/Miso`) |
| HV terminals | Pump / Valve / Neutral / Line | pump 9 (+ `pumpSensePin` 21), valve 10 |

Capabilities on this board: dimming + pressure (no ssrPump, no ledControls, no ToF).

### J6 expansion header (fork wiring to the Silvia front panel)

1x10 connector on the controller board; `extN` names map to `ControllerConfig` fields (`lib/GaggiMateController/src/ControllerConfig.h`), fork usage in `GaggiMateController.{h,cpp}`:

| Pin | Signal | Usage (this fork) |
|-----|--------|-------------------|
| 1–2 | +5V | power |
| 3 | +3.3V | power |
| 4 | GPIO13 (`ext5`) | unused |
| 5 | GPIO12 (`ext4`) | water rocker switch input → button index 2 |
| 6 | GPIO8 (`ext3`) | brew status LED (LED channel 8) |
| 7 | GPIO2 (`ext2`) | steam status LED (channel 9) |
| 8 | GPIO1 (`ext1`) | water status LED (channel 10) |
| 9–10 | GND | ground |

LED brightness semantics: 0 = off, 255 = solid, any other value = 1 Hz blink. Note: upstream uses ext2/ext3 as an I2C bus for addon autodetection (gearpump etc.) — this fork removed `detectAddon()` and repurposed those pins as LED outputs, so upstream addon-related changes to these pins must not be merged blindly.

## Fork changes vs upstream

The fork is ~15 commits ahead of upstream (fork point: upstream PR #827). Commit titles are unreliable (e.g. "Create Rancilio specific profile" actually introduced the momentary long-press flush) — trust the diff. The delta:

**Controller board firmware** (`lib/GaggiMateController/src/GaggiMateController.{h,cpp}`):
- `detectAddon()` removed — ext2/ext3 repurposed as LED outputs. **Permanently drops gearpump/XL9555 addon support.** Upstream changes touching addon detection or ext-pin usage must not be merged blindly.
- Third button: `waterBtn` on ext4/GPIO12 (Silvia water rocker), reported as button index 2.
- LED channels 8–10 are intercepted locally and driven on ext3/ext2/ext1 with blink handling in `updateModeLedOutputs()` (0=off, 255=solid, 64=fast blink, else 1 Hz); channels 0–7 still pass through to the Sunrise/Alba PCA9634, so the two features don't conflict.

**Display firmware** (`src/display/core/Controller.{h,cpp}`):
- Momentary-buttons mode ("brew" behavior in `setupBluetooth`): press edge deferred to release so tap ≠ hold; `checkBrewButtonLongPress()` (polled from `loopControl`) fires a **flush at 2 s mid-hold**, and the subsequent release is consumed.
- `handleBrewButton` in `MODE_WATER` now switches to brew mode (deactivate + `setMode(MODE_BREW)`) instead of activating the water pump.
- `handleWaterButton` in momentary mode toggles the pump on press (latching keeps stop-on-release).
- `updateModeLeds()`: per-mode status LED with thermal-state hysteresis (ready at target−1.5, back to heating at target−3 outside a shot, over-temp at target+3 / back at target+1.5) → slow blink heating / solid ready / fast blink over-temp. Sends LED channels 8–10, change-driven only.

**Simulator** (`sim/`):
- `sim/machine/MachinePanel.{h,cpp}` (fork-only dir): a rendered Silvia front panel in the SDL window — rocker switches inject button reports via `GaggiMateClient::simInjectButton()`, lamps show the firmware-driven mode LEDs, plus a manual steam-wand valve.
- `MockController`: wand-valve steam bleed on the thermal model, LED channel 8–10 state, `getSimState()` snapshot for the panel.

**Web UI** (`web/`): Rancilio logos replace the GaggiMate logo in `Navigation.jsx`, `emerald` added to allowed daisyUI themes, minor GeneralTab/style tweaks.

**LVGL UI**: regenerated from `eez-ui/gaggimate.eez-project` with a Rancilio look + `ui_image_rancilio` boot logo (the huge eez image-file diffs are regeneration artifacts, not hand edits).

## Note-taking (required)

The user wants meticulous notes on everything. Append a dated entry to `WORKLOG.md` (repo root, reverse-chronological) for every working session: what changed and why, decisions with rejected alternatives, sim/test verification results, pending items. Commit the worklog entry together with the change it describes. Promote durable facts (pinouts, semantics, commands) into this file. Git workflow: commit locally only, **never push** — the user pushes via GitHub Desktop; flag "push needed" with the commit hash and track it under Pending in the worklog.
